# Управление объектом и контрактом

02.11.2026. Отдельный срез от #29 (`e60b209`), PREPARED до review/CI/приёмки. Production остаётся на 11 миграциях; эта ветка содержит 13. Она не включается автоматически в #29, #24 или main. Hosted recovery в этом цикле не выполняется.

## Функциональный объём

Явно допущенный ответственный создаёт объект, меняет название/адрес/заказчика/контактные данные, архивирует и возвращает объект без удаления зданий и истории. Каждая карточка имеет optimistic version. Параллельный устаревший save получает 409, введённые данные сохраняются в форме до решения пользователя.

Контракт относится к одному неизменяемому site_id. Версия содержит номер, название, заказчика, исполнителя, период, статус, ответственного, опубликованное примечание, автора/время и отдельный PDF. Замена или продление добавляет новый снимок, не переписывает предыдущий. Изменение статуса/даты не закрывает заявки и не удаляет объект автоматически.

Клиент не видит черновой контракт только на основании членства в объекте. Менеджер отдельно подтверждает публикацию **выбранной** версии с её реквизитами и PDF. Добавление следующей версии оставляет клиенту прежнюю опубликованную. Можно выбрать другую версию либо снять публикацию без удаления истории; действия имеют append-only audit через API.

Клиент видит только текущую опубликованную версию своего объекта; её отзыв или отзыв членства блокирует следующий запрос файла. Уже скачанные копии отозвать нельзя. Публичные/signed URLs не создаются. Приложение выдаёт attachment с no-store/nosniff/sandbox, проверяя SHA-256; встроенного PDF preview нет.

## Права

facility_managers назначает только доверенный администратор. Активность service_staff **и** активная явная запись facility_managers обязательны. Никто не назначается миграцией. Обычный staff не получает права изменения через общую очередь, company или editable metadata.

| Актор                                | Карточка объекта                                   | Контракт/PDF                                                                           | Изменение и публикация                                       |
| ------------------------------------ | -------------------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Guest                                | Нет                                                | Нет                                                                                    | Нет                                                          |
| Клиент                               | Назначенные объекты                                | Только текущая публикация назначенного объекта                                         | Нет                                                          |
| Активный staff без manager admission | Общий реестр одной организации                     | Только опубликованные версии видимых объектов                                          | Нет                                                          |
| Активный staff с manager admission   | Общий реестр                                       | Все версии, включая внутренние                                                         | Create/edit site, append version, explicit publish/unpublish |
| Отозванный manager                   | Прежние обычные права staff/client, если сохранены | Внутренние версии закрыты; опубликованное может оставаться доступным по обычным правам | Нет                                                          |
| Неактивный staff                     | Только отдельное действующее клиентское членство   | Только публикации по такому членству                                                   | Нет                                                          |

Это одна обслуживающая компания, не multi-organization tenancy. Управление зданиями и назначение клиентского членства пока остаются административными. Реальные уполномоченные пользователи определяются до пилота; эта схема прав — реализация для review, не назначение production-ролей.

## Архитектурное решение для первого среза

В отличие от исходного направления с private Storage bucket, для ограниченного пилота выбран **закрытый PostgreSQL bytea**: один основной PDF до **2 MiB** на версию. Это позволяет сохранить метаданные, байты, digest и audit атомарно и включить файл в уже проверяемый DB backup/restore. Исходный план Storage не считается реализованным. Решение и предел требуют принятия до выпуска; приложения/сканы/Office и большие файлы остаются следующим этапом.

Файл лежит в private.contract_files, RLS включён. Схема private не экспонируется Data API. Публичный invoker download RPC читает только файл версии, доступной по RLS. Доступ проверяется на карточке и байтах. Server runtime использует пользовательскую SSR-сессию/publishable key; service-role ключ приложению не добавляется.

PDF проверяется по размеру, имени без path/control characters и `%PDF-` header. Это **не** антивирусная проверка или полный разбор PDF. Нет inline rendering; скачивание намеренно принудительное. SHA-256 выявляет несоответствие сохранённых байтов, не доказывает безопасность/подлинность документа.

Для потока больших файлов/многих версий нужен отдельный Storage backend с приватными policies, проверкой согласованности metadata/object и копированием самих objects в restore. Перенос требует новой миграции и проверки всех digest; текущие версии не удаляются. Автоматическая миграция в Storage/платные услуги не включены.

## SQL, API и конкурентность

Новая additive миграция `20261102123056_site_contract_management.sql` добавляет поля sites; public.facility_managers/contracts/contract_versions/contract_events и private.contract_files. Итого 11 public RLS tables и 13 maintenance triggers; private files также проверяются local verifier.

Authenticated получает SELECT, но не прямые DML для этих сущностей. Новые public mutation wrappers — SECURITY INVOKER; ограниченные private SECURITY DEFINER функции имеют empty search_path, явную manager-проверку, фиксированные SQL и отозванный PUBLIC/anon/service_role EXECUTE. Привилегия нужна для атомарной управляемой записи без раздачи прямых UPDATE/INSERT клиентам. Это чувствительная граница, требующая отдельного security review. Владелец БД/доверенный service_role остаётся административной границей доверия.

Стабильные draft UUID хранятся в URL формы; повтор exact payload не создаёт вторую карточку/версию/audit. Изменённый payload для использованного version ID получает 409. Advisory lock сериализует создание по ID, FOR UPDATE — изменение revision. Site version и contract revision защищают от stale updates; публикация также требует expected revision. Неподтверждённый ответ не повторяется автоматически: интерфейс предлагает проверить сохранённое. Reload сохраняет operation identity и показывает уже записанное.

Контракт и файл связывают deferrable FKs: committed версия не существует без файла, публикация не может указывать на чужой контракт. Manager API не предоставляет update/delete версии или байтов. Внутренний audit не выдаётся клиенту. Связи пользователей/истории RESTRICT; destructive down и hard delete в UI отсутствуют.

`POST /api/facility/manage` требует same-origin JSON, действующую Auth-сессию/manager admission, ограничивает поток тела 3 MiB без доверия Content-Length, проверяет поля/CAS и не раскрывает SQL errors. SQL повторно проверяет права и входные данные для прямого RPC. `GET /api/facility/files/[versionId]` проверяет Auth/RLS/digest и выдаёт generic denial для отсутствующих/недоступных байтов. Временный Auth/DB failure не называется успешной записью.

Все 5 новых изменяемых таблиц покрывает existing maintenance barrier, включая привилегированную запись. Чтение файла не требует открытия записи. Старый переход 8→11 не используется; отдельный delta rollout до production ещё нужен.

## Проверки

- M01: manager создаёт/редактирует site, replay не дублирует, stale editor получает 409 и не теряет draft.
- M02: membership/обычный staff/metadata не повышают роль; manager/staff revoke со старой сессией закрывает запись.
- M03: атомарные PDF+metadata, append-only версии, прежние bytes/author/history сохранены.
- M04: публикация отдельная, CAS защищён; клиент A видит выбранную версию, B/guest не получают известный UUID; будущая версия скрыта.
- M05: смена/отзыв публикации и членства меняет доступ к байтам без signed-link TTL.
- M06: filename traversal, non-PDF, >2 MiB, неверные даты/поля/parent IDs, CSRF/oversized body отвергаются.
- M07: lost acknowledgement не создаёт дубликат; форма сохраняет стабильный ID и не делает автоматический повтор.
- M08: maintenance не обходится private mutation; свежий и independent saved restore возвращают PDF/digest/права; rollback старого frontend сохраняет контракт и файл.

Suite: 46 unit/policy, 334 SQL / 10 файлов, 41 browser cases плюс расширенная server integration; counts — состав suite, PASS фиксируется только по фактическому CI конкретного SHA. SQL/browser/restore локально без Docker не запускались. CI использует owned ephemeral synthetic данные и PDF, без production credentials.

Fresh/saved restore fixtures теперь содержат две версии-контракта с PDF: один опубликован для клиента своего объекта, второй внутренний. Сверяются байты/digest, доступ клиента/outsider/staff/manager. Cleanup удаляет только owned fixture events → bytes → versions → contract в транзакции, затем manager admissions и прежние данные; циклические FK не обходятся отключением constraints. Preflight принимает новые таблицы только пустыми. Старый frontend rollback проверяет сохранность PDF через защищённый RPC, хотя сам старый frontend не показывает каталог.

Открыто перед выпуском: независимый review прав/definer RPC и выбранного binary storage, ручная приёмка, реальные роли/форматы/лимиты, собственный rollout/backup/rollback plan. Production и существующие recovery endpoints этим срезом не меняются. Следующее развитие — приложения/документы здания/private Storage и связь заявок с building_id, с сохранением legacy privacy.
