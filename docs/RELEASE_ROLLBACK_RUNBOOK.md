## Совместимость

- Старый main с восемью миграциями использует прежнюю запись.
- Рабочий контракт текущего интерфейса требует десять миграций: operation key и expected_version/RPC; локальный release-набор дополнен одиннадцатой миграцией обслуживания.

## При сбое

- До миграций: прервать выпуск, сохранить прежнюю проверенную пару app/schema.
- После миграций: оставить запрет записи, выяснить фактическую history, исправить вперёд либо вернуть совместимый frontend. Не удалять version/key/RLS/history ради старого UI.
- После открытия записи: закрыть затронутый поток, сохранить данные/логи без секретов, проверить совместимый target и canary перед возвратом.
- При потере/порче данных: сохранить источник, восстановить отдельно, сверить post-cutoff изменения и согласовать переключение. Не делать restore поверх production ради упражнения.
- При утечке: ограничить доступ, сохранить доказательства, определить область и согласовать rotation/session response. Не публиковать токены и не удалять пользователей ради деактивации.

Переключение deployment не откатывает БД/Auth/env. [Vercel Instant Rollback](https://vercel.com/docs/instant-rollback) зависит от тарифа/доступного target и отключает auto-assignment до promotion. Destructive down migration не подготовлена. Для этого выпуска локально проверен baseline 9d06996; облачного target ID ещё нет. Если совместимого target нет, сохранить обслуживание и готовить исправление вперёд.

Переключение Vercel не откатывает БД, Auth или env. Signing secret и канонические recovery URLs должны соответствовать обеим новым сборкам; при возврате нельзя автоматически вернуть старый Netlify URL/ConfirmationURL template. Отказ одного gate останавливает весь выпуск.
