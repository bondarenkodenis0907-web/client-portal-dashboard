# Объекты и здания — первый функциональный срез

02.11.2026. Ветка `feat/facility-directory-20261102` от `6c554ae` (#24). Статус PREPARED: реализация и изолированные проверки, не production release. По решению владельца продолжаем функции обслуживания, откладывая hosted recovery. Существующий recovery не удаляется; его приёмка не блокирует разработку этой ветки.

## Границы и архитектурное решение

Первый срез: постоянный реестр объектов, здания объекта, явный допуск клиента и серверные страницы просмотра. Карточки контрактов/файлы/оборудование/регламентные задания/связь заявок со зданием — следующие отдельные этапы. Пустая база показывает честное пустое состояние; демонстрационные объекты создаются только тестовыми fixtures изолированной среды.

Одна обслуживающая организация. Активный staff видит её реестр, как существующую общую очередь. Это не межорганизационная изоляция. Доступ клиента назначает доверенный администратор; company, user_metadata, наличие заявки с похожим текстовым site и UUID в URL не открывают объект.

| Сущность         | Поля / ограничения                                                      | Назначение                                                                                           |
| ---------------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| sites            | UUID, name 1–120 после trim, address ≤300, created_at                   | Реестр объектов; индекс name,id для стабильного порядка                                              |
| buildings        | UUID, site_id FK RESTRICT, name/address, created_at; UNIQUE(site_id,id) | Здание принадлежит ровно одному существующему объекту; составная уникальность для будущих request FK |
| site_memberships | PK(site_id,user_id), FKs RESTRICT, is_active, created_at                | Допуск клиента к объекту; partial index(user_id,site_id) WHERE is_active                             |

RLS включён на трёх таблицах. Authenticated имеет только SELECT, anon — никаких прав. Нет клиентских INSERT/UPDATE/DELETE, RPC с повышенными правами или права самозачисления. Административные записи service_role явно разрешены только серверному/доверенному инструменту; ключ не попадает в браузер. Существующий private.is_service_staff проверяет реальную активную запись, не editable metadata. Новых SECURITY DEFINER helpers не добавлено.

| Актор                                        | Sites / buildings                                         | Admissions                                           | Запись                                                                  |
| -------------------------------------------- | --------------------------------------------------------- | ---------------------------------------------------- | ----------------------------------------------------------------------- |
| Guest                                        | Нет                                                       | Нет                                                  | Нет                                                                     |
| Клиент с активным членством                  | Только свои объекты и их здания                           | Только свои строки                                   | Нет                                                                     |
| Клиент без членства / с отозванным членством | Нет соответствующего объекта/зданий                       | Своя строка может быть видна для диагностики допуска | Нет                                                                     |
| Активный staff                               | Общий реестр одной компании                               | Реестр допусков                                      | Нет: роль очереди не равна полномочиям управления                       |
| Неактивный staff                             | Только если отдельно есть действующее клиентское членство | Только свои строки                                   | Нет                                                                     |
| Доверенный администратор                     | Административный доступ                                   | Управление допуском                                  | Через закрытый инструмент; maintenance gate действует и на service_role |

Политика buildings следует видимости parent site через RLS. Membership SELECT не обращается к sites, поэтому рекурсии политик нет. Отзыв членства/деактивация staff действует при следующем запросе БД даже со старым JWT; уже загруженные в браузер данные отозвать нельзя.

Административный интерфейс и новая роль manager не вводятся до решения о полномочиях. Создание/изменение объектов через пользовательский UI пока не поддержано. Hard delete из UI отсутствует; FK RESTRICT предотвращает неявное каскадное удаление зданий/допусков. Политика архивирования и audit управления сущностями остаётся отдельным этапом.

## Серверный интерфейс

- `/dashboard/sites` — объекты, разрешённые RLS, 50 строк на страницу, exact count и порядок name,id.
- `/dashboard/sites/[siteId]` — карточка объекта и страницы зданий с порядком name,id.
- `/dashboard/sites/[siteId]/buildings/[buildingId]` — карточка здания; запрос проверяет оба ID, включая случай, когда staff видит оба чужих друг другу parent.
- Неверный UUID, отсутствующий и недоступный объект дают одинаковый экран недоступности. Сбой Auth/БД ведёт в retry boundary, а не в пустой список или ошибочный login.
- Server Components загружают только id/name/address своего пользователя. React.cache дедуплицирует получение SSR-клиента и getUser только внутри запроса; общего cache данных клиентов нет. Списки и parent/details не загружаются целиком в клиентский bundle.
- Existing request workflow, авторы, legacy site/system text, operation keys, version/history и приватность собственных заявок не меняются. Членство в объекте не даёт доступа к заявкам коллег.

## Схема и безопасное испытание

CLI создал новую additive миграцию `20261102114046_facility_directory.sql`. Ветка содержит **12 миграций**, 7 public RLS tables и 8 maintenance triggers. Production остаётся на **11** версиях; новая миграция туда не применялась. Не использовать старый переход 8→11 или общий db push против production.

Новые таблицы покрыты тем же maintenance barrier. Guarded local verifier проверяет их RLS/триггеры; restore preflight допускает только известные **пустые** новые таблицы и отказывает при данных. Исторический test-release-order по-прежнему репетирует только прежние 11 версий в отдельной временной БД; это не план применения новой миграции.

Synthetic restore сохраняет два объекта, два здания и два допуска, проверяет их права после fresh/saved restore. Cleanup удаляет только IDs своих fixtures в порядке children → parents → users; RESTRICT не обходится cascade. Архивные SQL tests продолжают определять собственные counts.

Rollback drill проверяет старый frontend `db0f9fb9` на текущей additive схеме, request continuity и сохранность новых directory rows через baseline → candidate → baseline. Старый frontend не показывает каталог, но не должен терять его данные. Cloud rollback старого выпуска и каталог в production этим не аттестуются. В случае отмены функций сохранять новые таблицы/данные; destructive down migration не подготовлен.

## Критерии приёмки и проверки

- F01: клиент A/B видит только свой объект/здания через UI и прямой API; отсутствующий допуск даёт пустой реестр.
- F02: прямой чужой UUID и несовпадающая пара site/building недоступны, в том числе активному staff с доступом к обоим объектам.
- F03: self-enrolment и записи клиента/staff запрещены; editable metadata не повышает роль.
- F04: отзыв membership и деактивация staff закрывают следующий запрос старой сессии; история прежних заявок не расширяет доступ.
- F05: name/address/FK/RESTRICT и maintenance защищают новые сущности; нет частичных записей после отказа.
- F06: стабильные серверные страницы 50+1 и для объектов, и для зданий; мобильная навигация 390 px, без горизонтальной прокрутки.
- F07: серверный Auth/DB 503 не становится пустым реестром; retry возвращает страницу без нового входа.
- F08: fresh/saved restore сохраняет directory rows/права, frontend rollback сохраняет каталог и заявки на новой схеме.

Постоянные проверки: 41 новых pgTAP assertions в `supabase/tests/facility_directory.test.sql` (всего 271 / 9 файлов), 3 новых browser-сценария (всего 38), расширенные server-side failure, restore safety/restore probes и rollback continuity. Эти числа описывают состав suite; результат фиксируется только после фактического запуска на конкретном SHA.

Локально SQL/browser/restore не выполняются без Docker. CI использует только ephemeral synthetic backend; production credentials и реальные данные не используются. Независимый security review схемы/матрицы и ручная приёмка перед merge/release остаются отдельным условием. Ветка не включается автоматически в #24 или main.
